# Roadmap — ยกระดับเป็น "Portal งานตรวจรับประจำตัว"

> บันทึกไว้ตามที่ผู้ใช้สั่งเมื่อ **27 ก.ค. 2569 (2026-07-27)** ยังไม่ได้ลงมือทำ
> รอคำสั่งเริ่มงานอีกครั้ง

---

## 1. เป้าหมาย

เปลี่ยนเว็บนี้จาก "ระบบตรวจรับพัสดุคอมพิวเตอร์ 49 รายการ (โครงการเดียว)"
ให้กลายเป็น **Portal ส่วนตัวสำหรับงานตรวจรับทุกโครงการที่ผู้ใช้ได้รับแต่งตั้งเป็นกรรมการ**
เนื่องจากคาดว่าจะได้รับแต่งตั้งเป็นกรรมการตรวจรับอีกหลายโครงการในอนาคต

### งานเฉพาะหน้าที่รออยู่แล้ว
* มีการตรวจรับ**ครุภัณฑ์**อีกหนึ่งโครงการ (ตรวจรับวันที่ 27 ก.ค. 2569) ซึ่ง**มีข้อมูลและรูปภาพประกอบพร้อมแล้ว**
* ต้องนำเข้าเป็นอีกโครงการหนึ่งในระบบ โดยไม่กระทบโครงการวัสดุคอมพิวเตอร์ 49 รายการเดิม

## 2. ข้อจำกัดที่ต้องยึดเป็นหลัก

> ⚠️ **ต้องอยู่บนแผนฟรีของ Firebase (Spark Plan) เท่านั้น** — ห้ามออกแบบอะไรที่บังคับให้ต้องอัปเกรดเป็น Blaze

โควตาที่เกี่ยวข้อง (ควรเช็กตัวเลขล่าสุดกับหน้า Firebase Pricing อีกครั้งก่อนออกแบบจริง):

| บริการ | โควตาฟรีโดยประมาณ | ผลต่อการออกแบบ |
|---|---|---|
| Cloud Firestore | ~1 GiB พื้นที่, ~50,000 อ่าน/วัน, ~20,000 เขียน/วัน | พอสำหรับหลายสิบโครงการ ถ้า**ไม่**ยัดรูปภาพลงไป |
| Firebase Hosting | ~10 GB พื้นที่, ~360 MB โอนต่อวัน | เหมาะกับการเก็บ**ไฟล์รูปภาพ**มากที่สุด |
| Firebase Storage | โปรเจกต์ที่สร้างใหม่มักต้องใช้ Blaze | 🚫 **หลีกเลี่ยง** — ผิดเงื่อนไขแผนฟรี |

### ข้อสรุปสำคัญเรื่องรูปภาพ
รูปภาพหลักฐาน **ไม่ควร**เก็บเป็น base64 ใน Firestore เป็นหลัก เพราะกินทั้งพื้นที่ 1 GiB และโควตาการโอนข้อมูล
แนวทางที่ควรใช้คือวางไฟล์รูปไว้ใน Hosting (โฟลเดอร์ `public/รูปภาพ/<projectId>/…`) แล้วเก็บแค่**ชื่อไฟล์**ใน Firestore
เหมือนที่โครงการ 49 รายการทำอยู่แล้ว ส่วนการอัปโหลดรูปหน้างานผ่านมือถือ (ซึ่งกลายเป็น base64) ให้คงไว้เป็นทางเลือกสำรอง
โดยมีการย่อรูปก่อนเก็บอยู่แล้วใน `readImageAsDownscaledDataUrl()`

## 3. สิ่งที่ "มีอยู่แล้ว" กับสิ่งที่ "ต้องทำเพิ่ม"

### ✅ มีอยู่แล้วในโค้ด (แต่ยังไม่ได้ต่อเข้าหน้าจอ)
* `inspectionRepository` รองรับหลายโครงการครบแล้ว — `listProjects` / `createProject` / `cloneProject` / `renameProject` / `deleteProject` / `exportProjectData` / `importProjectData` / `setActiveProjectId`
* ทะเบียนโครงการ `procurement_projects_registry_v1` และการ namespace คีย์ด้วย `projectId`
* คอมโพเนนต์ `src/components/ProjectManager.jsx` เขียนไว้แล้ว แต่ **`App.jsx` ยังไม่ได้ import มาใช้**
* ระบบแม่แบบการตรวจรับ (`inspectionTemplates.json`, `TemplateSettings.jsx`) ที่แยกชนิดพัสดุ/ครุภัณฑ์ได้

### ❗ ต้องทำเพิ่ม
1. **ต่อ `ProjectManager` เข้ากับ `App.jsx`** — เพิ่มตัวสลับโครงการ และหน้ารวมโครงการทั้งหมด (นี่คือหัวใจของ Portal)
2. **ขยาย Cloud Sync ให้รองรับหลายโครงการ** — ปัจจุบัน `src/utils/cloudSync.js` ตรึงไว้ที่ workspace เดียวคือ `projects/main`
   (ค่าคงที่ `CLOUD_PROJECT_ID`) ต้องเปลี่ยนเป็น `projects/{projectId}` และรองรับการสลับ listener เมื่อเปลี่ยนโครงการ
   พร้อมย้าย/รักษาข้อมูลเดิมใน `projects/main` ไม่ให้หาย
3. **ทะเบียนโครงการบนคลาวด์** — ตอนนี้ทะเบียนอยู่ใน localStorage เท่านั้น เครื่องอื่นจึงยังไม่เห็นรายการโครงการ
   ต้องย้ายขึ้น Firestore ด้วย (เช่น collection `projects` เก็บ metadata ของแต่ละโครงการ)
4. **แก้ `firestore.rules`** — ปัจจุบันอนุญาตเฉพาะ `projectId == 'main'` ต้องขยายให้ครอบคลุมทุกโครงการ
5. **แยกโฟลเดอร์รูปภาพตามโครงการ** — ปัจจุบันทุกภาพอยู่รวมใน `public/รูปภาพ/` และ `getImageUrl()` ชี้ไปที่ `./รูปภาพ/<filename>` ตรง ๆ
6. **`MAPPING_FIXES` ผูกกับโครงการเดิม** — ตารางจับคู่รูป 49 รายการใน `inspectionRepository.js` เป็นค่าตายตัวของโครงการวัสดุคอมพิวเตอร์
   ต้องกันไม่ให้ไป auto-heal รูปของโครงการอื่นผิด ๆ (ตอนนี้กันด้วย `noPhotoConfirmed` เท่านั้น)
7. **นำเข้าโครงการครุภัณฑ์ใหม่** — รับข้อมูล + รูปภาพที่มีอยู่แล้วเข้าสู่ระบบ

## 4. ข้อควรระวังตอนลงมือ

* **ห้ามทำข้อมูลโครงการ 49 รายการเดิมหาย** — ข้อมูลจริงอยู่บน Firestore ที่ `projects/main` แล้ว (ตรวจสอบเมื่อ 27 ก.ค. 2569: 49 เอกสาร, ผ่านตรวจรับ 49, งบรวม 245,010 บาท)
* ระบบสำรองอัตโนมัติก่อนงานที่เสี่ยง (`cloudSync.backupWorkspace`) ครอบคลุมเฉพาะ workspace ปัจจุบัน — ต้องขยายตามข้อ 2 ด้วย
* ปัจจุบันสิทธิ์เข้าถึงเป็นแบบ "ใครมีลิงก์ก็อ่าน/เขียนได้" หากกลายเป็น Portal ส่วนตัวที่รวมงานหลายโครงการ
  ควรพิจารณาเปลี่ยนเป็น Google Sign-in + allow-list อีเมล (ยังใช้ได้บนแผนฟรี)
